# Проверка изоляции тенантов и ролей

Критерий приёмки §21: «Пользователь одной компании не может получить данные другой компании». Ошибка здесь — главный риск продукта.

## 1. Инвентаризация
```bash
grep -rn "@router\.\(get\|post\|put\|delete\|patch\)" routes/          # все endpoint'ы
grep -rn "db.get(\|select(\|\.query(" routes/ services/                # все обращения к БД
grep -rn "business_id" routes/ | grep -v "BusinessContext"            # business_id вне контекста — подозрительно
```
Для каждого endpoint заполни строку: `метод путь | зависимость доступа | роли | фильтр по business_id | ответ на чужое`.

## 2. Правила, которые должны выполняться
- Защищённый endpoint получает пользователя/`BusinessContext` через зависимость из `services/access_service.py`. Endpoint без зависимости доступа — блокер (исключения: `/auth/register`, `/auth/login`, `POST /webhooks/telegram` — у него своя проверка секрета).
- Ресурсы «по id» (`/services/{id}`, `/conversations/{id}`, лиды, клиенты): сначала загрузить ресурс, затем проверить, что его `business_id` входит в компании пользователя. `db.get(Model, id)` без такой проверки = IDOR.
- Ответ на чужой ресурс — **404**, идентичный ответу для несуществующего (нельзя различить «нет» и «не твой»).
- Списки и аналитика: фильтр `business_id` в запросе, а не фильтрация в Python после выборки; агрегаты и счётчики — тоже.
- JOIN'ы и вложенные объекты: конечная таблица ограничена тем же `business_id`; `customers`, `messages`, `ai_responses`, `leads` достижимы только через `conversations` своей компании.
- Роли §5: OWNER — всё в своей компании; MANAGER — сообщения, лиды, ручные ответы, статусы, но не настройки/сотрудники/интеграции/тариф; ADMIN — `/admin/*`. Схемы входа не позволяют менять `role`, `business_id`, `owner_id`, `status` через body (mass assignment).
- `SUSPENDED` пользователь/компания не проходят авторизацию; отказ доступа пишется в аудит (`EventType.ACCESS_DENIED`).
- Секреты интеграций не возвращаются ни одним ответом.

## 3. Динамическая проверка
Убедись, что в тестах есть (иначе допиши в `smoke_test*.py`) для каждого нового endpoint:
1. Владелец A → свой ресурс: успех.
2. Владелец A → ресурс компании B: 404 (и данные B не просачиваются в тело/заголовки).
3. MANAGER A → owner-only действие: 403/404 по принятой схеме.
4. Без токена: 401.
5. Не-ADMIN → `/admin/*`: отказ.
```bash
python smoke_test.py
```
