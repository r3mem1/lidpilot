# Новый канал без переписывания ядра (§1, этап 9)

**Только после этапа 7 и подтверждённого спроса** — «несколько каналов одновременно» вне MVP (§19). Спроектируй план через `leadpilot-architect`, реализуй `telegram-integration-engineer`.

## Шаги
1. **Образец:** `integrations/telegram.py` и Protocol `ChannelClient` (`send_message(chat_id, text) -> external_id`). Новый канал — новый модуль в `integrations/` с тем же Protocol; ядро (`services/message_service.py`, `ai/`) не импортирует ничего канал-специфичного.
2. **Нормализация входа:** адаптер канала превращает payload в общий внутренний вид (канал, внешний id чата/сообщения, текст, отправитель). Если в `message_service` остались `if channel == "telegram"` — сначала вынеси их за Protocol/фабрику (отдельным коммитом, тесты этапа 3 зелёные).
3. **Схема:** `integrations.channel` и `conversations.channel` уже есть (§10) — проверь, что уникальность идемпотентности учитывает канал (`business_id + channel + external_message_id`); при изменении — миграция Alembic (скилл `add-endpoint`).
4. **Webhook:** отдельный маршрут вне списка §11 → пометка «вне ТЗ»; проверка подлинности по механизму канала (для WhatsApp — подпись `X-Hub-Signature-256` HMAC + verify-token), секрет — только хэшем/зашифрованно (инвариант 3); идемпотентность и «сначала сохранить, потом внешний API» (инвариант 4).
5. **Ограничения канала:** окна ответа, шаблоны сообщений, лимиты длины — в клиенте канала; ошибки без URL/токена в логах. Актуальный API — через MCP context7/fetch, не по памяти.
6. **Тесты:** `smoke_test_stageN.py` с `httpx.MockTransport`: неверная подпись → отказ; дубль → без второго ответа; сбой отправки → сообщение сохранено; изоляция компаний между каналами; регрессия: все прежние `smoke_test*.py` зелёные.
7. Скиллы после реализации: `telegram-webhook` (как эталон чек-листа), `tenant-isolation-check`, `ai-guardrails-check` (если менялся формат контекста).
