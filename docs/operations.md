# Эксплуатация LeadPilot (этап 7 — пилот)

Как устроен прод, как выкатывать и откатывать релиз, восстанавливать БД, менять секреты
и что делать при сбое. Разделы ТЗ: §16 (безопасность), §17 (логи и мониторинг),
§18 (надёжность). Значения секретов здесь не пишутся — только имена переменных.

## 1. Состав production

| Компонент | Где | Назначение |
|---|---|---|
| Приложение | Render, Web Service (Python 3.13, `.python-version`) | FastAPI: API, кабинет, `/admin`, webhook |
| БД | Supabase, PostgreSQL 17 (prod-проект) + отдельный dev-проект | Данные; dev — для проверки восстановления |
| Бэкапы | GitHub Actions: `backup.yml`, `restore-drill.yml` | Ежедневный зашифрованный дамп и проверка восстановления |
| Ошибки | Sentry (бесплатный тариф) | Оповещения о необработанных исключениях и ERROR-логах |
| Журнал | таблица `system_logs` → `/admin/events` | Аудит «что случилось с сообщением и почему» (§17) |
| Канал | Telegram Bot API, webhook `{PUBLIC_BASE_URL}/webhooks/telegram` | Бот каждой компании подключается из кабинета |

## 2. Настройки Render

Сервис на Render уже настроен и работает — его настройки являются источником истины.
Ниже — пример рабочей конфигурации и пояснения, **на случай пересоздания сервиса**
(новый аккаунт, переезд, восстановление после удаления). Менять работающий сервис не нужно.

Пример:

```text
Build:        pip install -r requirements.txt
Pre-Deploy:   alembic upgrade head
Start:        uvicorn main:app --host 0.0.0.0 --port $PORT --proxy-headers --forwarded-allow-ips='*'
Health Check: /health
```

Почему так:

- **Миграции до запуска:** схема меняется только Alembic (§18); если миграция упала,
  релиз не выкатывается и старая версия продолжает работать.
- **Без `--reload` и без `--workers`:** счётчик rate limit хранится в памяти процесса
  (`services/rate_limit_service.py`), при нескольких воркерах лимит перестанет быть общим.
  Общий счётчик (Redis) — этап 9.
- **`--forwarded-allow-ips`** при `FORCE_HTTPS=true`: TLS заканчивается на прокси Render; без доверия
  к `X-Forwarded-Proto` приложение считает запрос HTTP и зацикливает редирект. Если сайт открывается
  по HTTPS без ошибок — эта часть уже решена.
- **`/health`** не обращается к БД и не раскрывает конфигурацию.

**Environment** (обязательные для production; при ошибке приложение не стартует —
`_check_production_safety` в `main.py`):

| Переменная | Значение на проде |
|---|---|
| `ENVIRONMENT` | `production` (закрывает `/docs`, включает проверки при старте) |
| `DATABASE_URL` | Supabase, `postgresql+psycopg2://…` (Session pooler) |
| `JWT_SECRET` | случайная строка ≥ 32 символов |
| `SECRETS_ENCRYPTION_KEY` | отдельная случайная строка ≥ 32 символов (не выводить из JWT_SECRET) |
| `PUBLIC_BASE_URL` | `https://…` — адрес сервиса, на него регистрируется webhook |
| `FORCE_HTTPS` / `AUTH_COOKIE_SECURE` | `true` / `true` |
| `DEBUG` / `AUTO_CREATE_TABLES` | `false` / `false` |
| `TRUSTED_PROXY_COUNT` | `1` (прокси Render); иначе rate limit видит IP прокси, а не клиента |
| `AI_PROVIDER`, `AI_API_KEY`, `AI_MODEL` | реальный провайдер (`stub` на проде запрещён) |
| `BOOTSTRAP_ADMIN_EMAIL`, `BOOTSTRAP_ADMIN_PASSWORD` | первый ADMIN; после первого входа пароль можно убрать из окружения |
| `SENTRY_DSN` | необязательно: DSN проекта Sentry; пусто — трекер выключен, сайт работает как раньше |
| `SYSTEM_LOGS_RETENTION_DAYS` | необязательно: по умолчанию `90` (см. §6) |

Секреты GitHub Actions (репозиторий **Private**): `PROD_DATABASE_URL`, `DEV_DATABASE_URL`,
`BACKUP_PASSPHRASE`.

## 3. Выкатка релиза

1. Локально зелёные `python scripts/run_checks.py` и `python scripts/run_checks.py lint`.
2. `git push` в `main` → Render собирает, выполняет `alembic upgrade head`, переключает трафик
   после успешного `/health`.
3. После выкатки: `/health` отвечает, в `/admin/events` нет новых ERROR, в Sentry нет новых проблем.
   Отправить тестовое сообщение боту демо-компании и убедиться, что ответ пришёл.

**Миграции должны быть обратно совместимыми** (сначала добавить колонку/таблицу, код переключить
следующим релизом, удалить старое — ещё позже). Тогда откат кода не требует отката схемы.

## 4. Откат релиза

1. Render → сервис → **Events** → предыдущий успешный деплой → **Rollback**. Код возвращается
   за минуту; миграции при этом **не** откатываются.
2. Если новая миграция несовместима со старым кодом: сначала бэкап (Actions → db-backup →
   Run workflow), затем локально с `DATABASE_URL` прода `alembic downgrade -1`, затем Rollback.
3. Запись об откате и причине — в описание инцидента (§9).

Пока сервис недоступен, сообщения не теряются: Telegram повторяет доставку webhook до ~24 часов,
а сообщения, застрявшие после сбоя AI/Telegram, подхватывает фоновая повторная обработка
(`REPROCESS_INTERVAL_SECONDS`, `MESSAGE_MAX_ATTEMPTS`).

## 5. Бэкапы и восстановление БД

**Бэкап** (`.github/workflows/backup.yml`): ежедневно в 03:17 UTC, `pg_dump` 17 схемы `public`,
проверка, что в дампе есть таблица `users`, шифрование GPG AES-256 фразой `BACKUP_PASSPHRASE`.
Артефакт `leadpilot-db-backup` хранится **30 суток**. Ручной бэкап — Actions → db-backup →
Run workflow (делать перед рискованной миграцией и восстановлением).

**Проверка восстановления** (`restore-drill.yml`, вручную): последний бэкап расшифровывается
и восстанавливается в **dev**-проект Supabase, печатаются счётчики строк основных таблиц.
Запускать **раз в месяц** и после изменения схемы. Бэкап без проверенного восстановления не считается рабочим.

**Восстановление prod** (потеря или порча данных):
1. Render → сервис → **Suspend**: остановить запись в БД. Telegram накопит апдейты и дошлёт после запуска.
2. Скачать нужный артефакт (Actions → запуск db-backup → Artifacts) и расшифровать:
   `gpg --decrypt --output leadpilot.dump leadpilot-<дата>.dump.gpg`.
3. Сначала восстановить в dev и проверить данные (как в `restore-drill.yml`).
4. Восстановить в prod тем же клиентом 17:
   `pg_restore --clean --if-exists --no-owner --no-privileges --dbname="$PROD_URL" leadpilot.dump`
   (`PROD_URL` — строка подключения без `+psycopg2`).
5. `alembic upgrade head` (если дамп старше последней миграции) → Render **Resume**.
6. Проверить вход, `/admin`, тестовое сообщение боту; записать инцидент.

Данные, записанные после бэкапа и до сбоя, теряются: худший случай — сутки (RPO 24 ч).

## 6. Журнал system_logs и срок хранения

- События старше `SYSTEM_LOGS_RETENTION_DAYS` (по умолчанию 90 дней) удаляются фоновой задачей
  раз в `SYSTEM_LOGS_PURGE_INTERVAL_HOURS` (24 ч; первый запуск — при старте), пачками по 5000.
- **Не удаляются никогда** критические действия ADMIN: смена статуса компании, тарифа,
  создание администратора и сами записи об очистке (`audit_service.RETAINED_EVENT_TYPES`).
- Каждая очистка пишет событие `SYSTEM_LOGS_PURGED` (сколько удалено и граница по дате).
- Следствие: на вопрос «почему бот ответил именно так» журнал отвечает за последние 90 дней.
  Сами сообщения, ответы AI (`ai_responses`) и лиды не удаляются. Старые события остаются
  в бэкапах (30 суток).
- `0` — хранить бессрочно (тогда следить за размером БД: бесплатный Supabase — 500 МБ).

## 7. Мониторинг и оповещения

| Что | Где смотреть | Кто оповещает |
|---|---|---|
| Необработанные исключения, ERROR-логи | Sentry | Sentry → Alerts → «A new issue is created» → email |
| Ошибки AI, Telegram, отправки; эскалации | `/admin/events` (фильтр по уровню ERROR/WARNING) | — (смотреть ежедневно на пилоте) |
| Ошибки за 24 часа по платформе и компаниям | `/admin` — обзор | — |
| Доступность | Render health check `/health` | Render → Notifications → email при сбое деплоя/сервиса |
| Бэкап не прошёл | GitHub Actions | email GitHub о падении workflow |

В Sentry не отправляются тела запросов, заголовки, query-строки, локальные переменные,
токены ботов, Bearer-токены и email (`monitoring.py`). Персональные данные клиентов бизнеса
в Sentry не попадают.

## 8. Ротация секретов

| Секрет | Как сменить | Последствия |
|---|---|---|
| `JWT_SECRET` | новое значение в Render → деплой | все пользователи выходят из кабинета; иных последствий нет |
| `SECRETS_ENCRYPTION_KEY` | новое значение в Render → деплой → **каждая компания переподключает бота** в «Настройках» | старые `enc:…` токены становятся нечитаемыми (перешифровки нет): до переподключения входящие сохраняются, но ответы получают окончательную ошибку отправки и сами не повторяются — менеджер отвечает вручную после переподключения. Менять только при компрометации |
| Секрет webhook компании | переподключить бота в «Настройках» | генерируется новый, в БД — только SHA-256 |
| Токен бота компании | `/revoke` в @BotFather → новый токен → переподключить в «Настройках» | — |
| `AI_API_KEY` | новый ключ у провайдера → Render → деплой → отозвать старый | — |
| Пароль БД | Supabase → Database → Reset password → обновить `DATABASE_URL` (Render) и `PROD_DATABASE_URL` (GitHub) | без обновления GitHub-секрета перестанут создаваться бэкапы |
| `BACKUP_PASSPHRASE` | новое значение в GitHub | бэкапы за прошлые 30 суток расшифровываются **старой** фразой — хранить её, пока они не истекут |
| `SENTRY_DSN` | Sentry → Client Keys → новый ключ → Render | — |

Секреты хранятся в менеджере паролей владельца; в чат, код, логи и тикеты не копируются (§16).

## 9. При инциденте

1. Оценить масштаб: `/admin` (ошибки за 24 ч), Sentry, Render → Logs.
2. Сообщения клиентов не теряются (§18, §21 п.15): входящие сохраняются до вызова AI/Telegram,
   необработанные подхватит повторная обработка. Проверить в `/admin/events` события
   `MESSAGE_PROCESSING_FAILED`, `MESSAGE_SEND_FAILED`, `AI_ERROR`.
3. Сбой провайдера AI: ответы уходят в эскалацию менеджеру, это штатно. Сбой Telegram: ответы
   повторяются. Компанию с аномалиями можно временно перевести в `suspended` в `/admin`
   (AI перестанет отвечать, входящие сохраняются).
4. Регрессия после релиза → откат (§4). Порча данных → восстановление (§5).
5. Утечка секрета → ротация (§8).
6. Записать: что случилось, время, затронутые компании, причина, что исправлено.
